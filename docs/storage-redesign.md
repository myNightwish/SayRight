# 存储核实与后续改造建议（2026-10-28）

## 当前事实

- 这份服务端代码连接 Upstash Redis；每个访问身份的同步桶保存整份 JSON，同步使用 Lua 比较并写入（CAS）避免两个设备无条件覆盖同一旧版本。
- 浏览器 / 插件先写 localStorage 或 chrome.storage.local，再通过 /sync 合并 corrections、drillState 等映射。关系、版本和删除传播主要由应用代码维护。
- Supabase 插件当前返回一个 INACTIVE 项目。当前服务端没有 Supabase 连接或查询代码，不能将这个项目的状态解释为此次替换失败的原因。
- 用户确认故障入口是 chrome-extension:// 的收藏页。网页侧同一已审核例句可以替换并在刷新后保留；它不能证明用户运行中的插件 worker 已更新。
- 浏览器工具禁止读取 chrome-extension://，因此未直接确认用户 worker 的版本，未将“旧 worker”认定为已经证实的根因。

## 本次替换链路改动

- 新增 worker 能力握手。旧 worker、缺少协议号或通信断开时，卡片内提示重新加载插件，避免页面与后台功能不一致却继续操作。
- 替换错误在按钮旁显示，避免错误只留在页面顶部。
- 保存前检查异步备份期间原句是否发生变化；保存后重新读取并核对主句及已审核记录 ID，未持久化不能报告成功。
- 新替换版本大于已存在的表达版本，覆盖设备时钟较快造成的新操作版本反而较旧的边界情况。
- 使用模拟的真实插件调用链（页面消息 → 后台 listener → chrome.storage.local）验证；尚需用户更新并重载实际插件确认。

## 建议的目标结构

JSON 本身是合适的数据类型。建议将长期业务实体逐条存储，AI 的可变反馈保留为 JSONB，不将整个产品状态放进一个文档后每次全量合并。

| 实体 | 主要内容 |
| --- | --- |
| expressions | 稳定 ID、所有者、原句、当前主句、情境、来源、状态、版本、删除状态 |
| practice_attempts | 对应表达及轮次、审核时参考句、用户原始造句、审核结果、AI 反馈 JSONB |
| practice_windows / window_items | 本轮、最多 10 个已确认位置、候补之外的实际成员、自评及对应表达版本 |
| expression_revisions | 替换前后文本、所依据的审核记录、时间，保留历史 |

替换应是一次服务端事务：核对身份、审核结果和原句版本 → 更新主句 → 记录版本历史。并发版本变化返回冲突，用户重试，不静默报告成功。后续按记录或变更游标增量同步，浏览器保留离线缓存。

Supabase 已提供托管 PostgreSQL。Render 可继续用现有 Web Service 承载网页和 API；本机模型桥接可以保留。网页、本机服务和插件共享同一个生产数据库，开发测试数据独立，避免意外覆盖真实资料。无需另行自建一台数据库服务器。

## 迁移约束

1. 导出并保留 Redis 与各客户端未同步数据，包含原句、当前句、来源、墓碑、造句、评分和轮次记录；避免只备份线上快照而遗漏离线改动。
2. 先编写转换及校验程序，保留旧 key 与新 ID 的映射；导入后逐条比对内容、数量、删除状态和历史关联。
3. 校验完成前继续以旧存储为准。切换时处理迁移期间的增量，防止两套可写存储长期并行。
4. 新接口生效后，旧客户端提示升级，旧库保留为只读备份并准备回滚方案。
5. 迁移前先恢复或选择可用 Supabase 项目，并确认身份及访问控制。当前没有执行数据库迁移或生产数据写入。
